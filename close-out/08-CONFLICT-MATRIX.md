| **الطرف أ** | Blueprint §4، السطر الأول: «كل فريق طبي (Mafraza) = مستأجر (Tenant) مستقل منطقيا داخل نفس قاعدة البيانات» |
| **الطرف ب** | الخارطة §2.2.2 + ملف المفرزة §1: «Tenant model is now **confirmed**: one tenant can hold multiple مفارز» |
| **الفائز** | **ب**، بثلاث جهات مستقلة: ملف المفرزة يعلنها «confirmed»، والخارطة تبنيها في المخطط، وأمر العمل §2 ينصّ نصّا «One tenant holds multiple مفارز» |

## ت‑3 · PowerSync ضدّ بروتوكول المزامنة المخصّص

| | |
|---|---|
| **الطرف أ** | أمر العمل §2: «offline-first via PowerSync» |
| **الطرف ب** | ثلاثة مستندات متّفقة: Blueprint §8 = polling + delta sync · ملف المفرزة §5 = `pendingSync` + `sync_deletion_outbox.dart` والهدف يتحوّل من Supabase إلى NestJS · الخارطة §8.6 = بروتوكول cursor مخصّص |
| **الفائز** | ~~لم أحسم~~ **← منسوخة.** كانت: «ثلاثة مستندات مصدر متّفقة ضدّ ذكر واحد في أمر العمل — وأمر العمل أعلى حجّية، فلا يجوز إسقاط ذكره؛ لكن الحسم لصالحه يُلغي تصميما موصوفا في ثلاثة مواضع، وهو أكبر من أن يُحسم بلا جوابك». **والحاصل الآن: ب** |
| **ملاحظتان تقنيّتان تزيدان الشكّ** | (1) PowerSync تتعارض ظاهريا مع **«no direct-to-DB client calls»** الواردة في **الفقرة نفسها** من أمر العمل. (2) نموذج RLS يمرّر سياق المستأجر بـ `SET LOCAL` في معاملة الطلب عبر `nestjs-cls`؛ ومزامنة تتصل بقاعدة البيانات بمسار آخر تحتاج مسار تفويض منفصلا لا يوجد له تصميم في أي مستند |
| **ما يُترتّب شرطيا** | **إذا cursor مخصّص → نطاق الكاش يُحدَّد باستعلامي، واستثناء `patients.condition` يُنفَّذ في طبقتي (R1).** **إذا PowerSync → قواعد النطاق تُكتب في تعريف مجموعات المزامنة عند المزوّد، ويجب إثبات استثناء `condition` هناك قبل أي إطلاق، وتُعاد كتابة مفاتيح `MTM_SYNC_*` في `09`، ويتغيّر مضمون المرحلة 3 في `10`** |
| **الحالة** | ~~`[FLAG-1]`~~ → **مفضوض ✅ (25 أغسطس 2026): الفائز ب — بروتوكول cursor مخصّص، وPowerSync مرفوضة** (`12`/`FLAG-1`) |

> **ولماذا فُضّ لصالح الأدنى حجّية، وهذا ليس خرقا للسلّم:** أمر العمل أعلى، لكن ما فيه **ذِكر** لا **تصميم**، والذكر يتعارض مع الفقرة نفسها («no direct-to-DB client calls»). فالسلّم يُرجّح المستند الأعلى عند **تصميمين متنافسين**، لا عند اسم مزوّد مقابل ثلاثة تصاميم متّفقة. **والفرع الشرطي الثاني أعلاه سقط بكامله**، ومعه إثبات الاستثناء عند المزوّد ومعالج فرعي في الـ DPA.

## ت‑4 · عشر مراحل ضدّ إحدى عشرة

| | |
|---|---|
| **الطرف أ** | Blueprint §14: عشر مراحل مرقّمة 1–10، **بلا مرحلة 0** |
| **الطرف ب** | الخارطة §18: **إحدى عشرة مرحلة 0–10**، والمرحلة 0 «الأساس والعزل» بوّابة حاكمة |
| **الفائز** | **ب** — ووثيقة الإغلاق (حجّية 2) تحيل صراحة إلى «Phases 0–10»، فتحسم لصالح ترقيم موجود في مستند مكتوب |
| **لماذا لا يُعدّ اختراع مخطّط مواز** | أمر العمل §4 يمنع «اختراع مخطّط ترقيم مواز». ترقيم 0–10 **ليس اختراعي** — هو مكتوب في الخارطة §18 بأسمائه. ما فعلته هو اختيار أحد ترقيمين موجودين وتسمية الفارق، لا إنشاء ثالث. جدول المطابقة الصريح بين الترقيمين في `10` |
| **الوجه الجوهري لا الشكلي** | الـ Blueprint يبدأ من «الأساس» كعمل عادي؛ الخارطة تجعل المرحلة 0 **بوّابة لا تُعبَر قبل نجاح اختبارات العزل**. الفارق ليس رقما بل وجود بوّابة تمنع البناء فوق عزل غير مُثبَت — وهذا هو الضابط الأهم في المشروع كله |
| **أثره على الـ 19 بندا** | **كان** `CO-D2` وَ`CO-D5` يحجزان المرحلة 0، وقد حُسما فصارت البوّابة **ستّة شروط آلية** · **L1** وَ**L4** في المرحلة 7 · `CO-D3` في المرحلة 8 (يحجزها الآن **G4** وحده) · **وأُضيفت مرحلة ثانية عشرة: 1.5** |

> **ولماذا اسمها «1.5» ورقم صحيح لم يُستعمل:** إدخالها كـ «2» يُزحزح تسعة أرقام مستعملة في `10` و`09` و`04` والخارطة — وهذا **بالضبط** «اختراع مخطّط ترقيم مواز» الذي يمنعه أمر العمل §4. الكسر يُضيف مرحلة **بلا لمس رقم قائم**: العدد صار اثنتي عشرة، **والترقيم لم يتغيّر**. وصفّ ت‑4 يبقى «10 ضدّ 11» لأنه يوصّف الخلاف **بين المستندين المصدر**، لا حصيلة هذه الحزمة.

## ت‑5 · نطاق Super Admin — ~~لا يُحسم هنا~~ **مفضوض ✅**

| | |
|---|---|
| **الطرف أ** | Blueprint §5: «**Super Admin:** مالك المنصة (أنت)… **Main Admin:** أعلى صلاحية داخل كل مستأجر» · ويعزّزه §9.3 (كل إعدادات Super Admin على مستوى المنصّة) و§9.5 (`Super Admin ← Main Admin ← Admin`) |
| **الطرف ب** | ملف المفرزة §1 بند 3: «The signer-upper becomes that tenant's Super Admin — ***interpretation, flagging it***… If you meant Super Admin to be platform-ops-only (you), the person who signs up should land as Main Admin instead — one-line change if so» |
| **الواقعة المحسومة** | **النصّ يدعم الطرف أ.** الـ Blueprint حجّية أعلى وصريح في ثلاثة مواضع، والطرف ب **يصف نفسه أنه تفسير** ويعرض البديل بنفسه |
| **الخيار — كان غير محسوم** | «أي نموذج **تختاره أنت** — قاعدة 12 تفصل حسم الواقعة عن حسم الخيار. الخيارات في `01` تحت `CO-D5`». **الجملة منسوخة** |
| **الحالة** | **مفضوض ✅ (25 أغسطس 2026): الفرع أ — Super Admin دور منصّة حصرا، والمسجِّل يصير Main Admin** (`12` §12.3). والواقعة والخيار **اتّفقا**: النصّ كان يدعم أ، والقرار جاء على أ — وقاعدة 12 هي التي منعت الخلط بينهما حتى وقع ذلك |

> **وما لم يكن في الخيار حين عُرض:** الحدّ صار **فيزيائيا** لا منطقيا فقط — مضيف مستقلّ (`admin.<domain>`) ومُصادِق مستقلّ (مفتاح مرور) وهدف بناء مستقلّ (`lib/main_admin.dart`) ودور قاعدة بيانات مستقلّ (`platform_writer`). **الفرع أ كان يعني «لا يظهر في جدول أدوار المستأجر»، وصار يعني «لا يشترك معه في سطح تنفيذ»** — والزيادة ثمنها `R4`.
